# Отчет по лабораторной работе №9 (Итоговая защита)

**1. Архитектура проекта:**
Проект `incident-collect` состоит из главного диспетчера и набора параллельных сборщиков. Диспетчер разбирает аргументы, подготавливает среду и запускает сборщики (ОС, память, диски, логи, сеть) через пул воркеров, используя `wait -n`. Результаты сохраняются в `raw/`, маскируются и агрегируются в единый `report.md` и `report.json`.

**2. Обработка сигналов и тайм-аутов:**
*Тайм-ауты*: Каждый сборщик обернут в `timeout 10s`. Если команда зависает, она убивается, а в лог пишется ошибка.
*Сигналы*: Обработчик `trap cleanup EXIT INT TERM` перехватывает прерывания (например, Ctrl+C). Он не выполняет сложную логику, а просто рассылает `SIGTERM` всем запущенным фоновым процессам (`jobs -pr`), чтобы не оставить «висящих» сборщиков. После этого скрипт завершается с кодом 130.

**3. Пример отчета без утечки секретов:**
В секции LOGS строка `Connecting to DB with password=supersecretpass` будет автоматически преобразована в `Connecting to DB with password=***` благодаря модулю `redact_file`.

**4. Пять ограничений Bash как языка для системной автоматизации:**
1. **Нет многопоточности**: Приходится использовать фоновые процессы и `wait`, что усложняет обмен данными (через файлы).
2. **Сложная обработка структур данных**: В Bash нет объектов, списков и хеш-таблиц (ассоциативные массивы есть, но работают медленно). JSON парсится только утилитами вроде `jq`.
3. **Отсутствие строгой типизации**: Все переменные — строки. Опечатки ловятся только на этапе выполнения (даже с `set -u`).
4. **Хрупкость обработки текста**: Регулярные выражения (grep/sed) сильно зависят от версии утилиты и локали (Linux vs macOS vs Windows).
5. **Уязвимости безопасности**: Легко случайно допустить инъекцию команд (Command Injection), если не заключать переменные в кавычки или использовать `eval`.
