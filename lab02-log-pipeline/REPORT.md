# Отчет по лабораторной работе №2: Анализатор логов

## 1. Модель времени и часовой пояс
В логах время представлено в формате ISO 8601 (UTC). Скрипт `log-report` извлекает это время и работает с ним как со строкой, не выполняя конвертацию в локальное время. Это сделано намеренно: работа с UTC исключает ошибки при переходе на летнее/зимнее время и гарантирует, что логи, собранные с разных серверов в разных часовых поясах, будут корректно сопоставлены.

## 2. Почему перцентили требуют хранения выборки (компромисс)
Для вычисления точных перцентилей (p50, p95, p99) необходимо знать распределение всех значений. В нашем решении мы накапливаем все значения времени ответа в массив внутри `awk` и в конце вызываем `asort` для сортировки. 
**Компромисс**: Это требует O(N) памяти. Для логов в 100 000 строк (как в нашем тестовом задании) это около 1-2 МБ ОЗУ, что абсолютно безопасно. Однако для файлов размером в десятки гигабайт этот подход приведет к исчерпанию памяти (OOM). Альтернативы (внешняя сортировка через `sort -n` или алгоритмы аппроксимации вроде t-digest) работают медленнее или сложнее в реализации на чистом Bash/awk.

## 3. Нормализация и агрегация
Нормализация (парсинг строки и извлечение полей) и агрегация (подсчет сумм, топов и сбор времен) происходят в одном проходе `awk`. Это обеспечивает сложность O(N) по времени и дисковому вводу-выводу (файл читается ровно один раз). Разделение этих этапов на два разных скрипта потребовало бы промежуточной записи на диск, что замедлило бы работу.

## 4. Ответы на контрольные вопросы

1. **Почему `awk` часто лучше цепочки из множества `grep`?**
   Цепочка `grep | grep | grep` читает файл столько раз, сколько команд в конвейере. Кроме того, `grep` не умеет производить математические вычисления (суммировать байты, считать перцентили). `awk` же позволяет за один проход по файлу распарсить строку, проверить условия (статус, IP) и сразу обновить счетчики в памяти.

2. **Как локаль влияет на сортировку и сравнение чисел?**
   В разных локалях по-разному сортируются строки (регистр, буквы с диакритикой) и по-разному записываются десятичные дроби (запятая вместо точки). В Bash-скриптах по умолчанию лучше использовать `export LC_ALL=C` для сортировки (`sort`), чтобы гарантировать предсказуемый байтовый порядок (ASCII). В нашем скрипте мы избегаем сортировки чисел с плавающей точкой, используя целочисленные миллисекунды.

3. **Какие ограничения есть у Bash при обработке NUL-байтов?**
   Bash использует C-строки, которые завершаются NUL-байтом (`\0`). Поэтому переменные Bash не могут хранить NUL-байты. Если попытаться прочитать бинарный файл с `\0` в переменную, Bash просто обрежет строку на первом `\0`. Именно поэтому мы используем `-print0` в `find` и не пытаемся обрабатывать бинарные данные чисто встроенными средствами Bash.

4. **Как оценить сложность конвейера и его дисковый профиль?**
   Сложность конвейера оценивается по Big-O от количества строк: O(N) для одного `awk` лучше, чем O(N*K) для `K` последовательных вызовов `grep`. Дисковый профиль: если файл читается один раз, это Sequential Read (быстро). Если данные пишутся на диск в промежуточные файлы, это добавляет Random/Sequential Write (медленно). Наше решение читает файл один раз и держит промежуточные данные в памяти, минимизируя дисковый I/O.
